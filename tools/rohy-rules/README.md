# rohy rules for VS Code

Checks and formats [rohy](../../README.md) correlation rule files while you edit them.

## How a file is checked

The status bar, beside a rule file, says which of two checks is in use:

- **`✓ rohy`: `rohyctl` was found.** The buffer is checked as you type, by `rohyctl validate`.
  That is the same function the application loads rules with, so a file with no problems here
  is a file that loads. Errors and warnings appear where they are, with their codes.
- **`ⓘ rohy: schema only`: `rohyctl` was not found**, or cannot be used. VS Code checks the file
  against the rule schema (`schemas/rohy-rule.schema.json`, generated by `tools/genschema`), and
  hover and completion work. The schema describes the shape of a rule. It cannot express anything
  that depends on the algorithm, so a file with no problems may still not load. The tooltip says
  why `rohyctl` is not in use.

`rohy: Show Log` (or a click on the status bar item) says which `rohyctl` was found and where.

**Format Document** lays a rule out in the house style with `rohyctl format`. That is the layout
the built-in library uses, and the one `rohyctl format --check` holds a CI job to. It needs
`rohyctl`. A file that does not parse is left as it is, and you are told why. VS Code may ask
once which JSON formatter to use for these files.

## Which files

- `rohy-data/rules/*.json`: the application's rules folder. `rules-state.json` sits there too,
  and is not a rule; it is left alone.
- `backend/rules/builtin/*.json`: the built-in library, in a checkout of rohy itself.
- Anything matched by `rohy.ruleFiles`.

## Settings

| Setting | Default | |
|---|---|---|
| `rohy.rohyctlPath` | empty | The absolute path of the `rohyctl` to use. Empty means the first `rohyctl` on `PATH`. A path that is wrong is reported, never replaced by another `rohyctl`. |
| `rohy.ruleFiles` | `[]` | More glob patterns for rule files. A pattern with no root matches anywhere: `rules/*.json` means any `rules` folder. These files are checked and formatted by `rohyctl`; the schema's hover and completion cover only the default folders, because VS Code reads that list from the manifest. |

## Safety

- **An opened folder cannot choose the program that runs.** `rohy.rohyctlPath` is read only from
  your user settings, never from a folder's. `PATH` is searched by the extension itself, in
  absolute entries only, so a `rohyctl.exe` placed inside a repository is never picked up from
  the current directory. On Windows only `rohyctl.exe` is taken, never a `.cmd` or `.bat`.
- **The text goes on stdin**, never on the command line, and there is no shell. Nothing typed in
  a rule can become an argument.
- **Every run is bounded:** 10 seconds, 8 MiB of output, and cancelled when the text changes
  again. The output is checked field by field. A report the extension cannot read is reported
  as an error, never shown as a file with no problems.
- `rohyctl` never opens a case. It reads the text it is given and nothing else.

This is why the extension declares full support for folders you have not trusted: it behaves
the same in them.

## Versions

The extension has its own version, independent of rohy's. Its first release is 0.1.0.

It works with any `rohyctl` whose `validate --json` report is in shape 1 (`output_version`). A
`rohyctl` that reports another shape is refused, with a message naming both shapes, and is never
read as a file with no problems. The schema it falls back to is copied in when the extension is
packaged, so in that mode it checks the rule format of the rohy it was built from.

## Building and testing

There are no dependencies. The tests use Node's own runner and need Node 22 or later:

```sh
cd tools/rohy-rules
npm test
```

`rohyctl validate --json` is the contract between the two halves. The rules in
`test/fixtures/rules` and the reports in `test/fixtures/reports` are read by both test suites:
the Go test (`cmd/rohyctl/validatejson_test.go`) pins what `rohyctl` prints for each rule, and
these tests place those exact reports on those rules. To change the output on purpose:

```sh
go test ./cmd/rohyctl/ -run TestValidateJSONMatchesTheExtensionFixtures -update-extension-fixtures
```

Then check the diff, and that `npm test` still passes.

To build an installable package (this fetches `@vscode/vsce` at packaging time; it is not a
dependency of the extension):

```sh
npx @vscode/vsce package
code --install-extension rohy-rules-0.1.0.vsix
```

### Checked by hand

The tests drive the extension through a fake VS Code API. They cover which files are checked,
when, and which answer is kept. What only a real VS Code can show is checked by hand, after
installing the package:

1. Open a rule in `rohy-data/rules/`. The status bar reads `✓ rohy`. Type `"algorithm": "x"`:
   the squiggle lands on `"x"` within a moment, with the code `unknown_algorithm`.
2. Open `rules-state.json` in the same folder: no status bar item, and no problems.
3. Run **Format Document** on a rule with tabs: it is laid out in the house style.
4. Set `rohy.rohyctlPath` to a path that does not exist: a warning names the setting, and the
   status bar reads `schema only`.
5. Add `"rohy.rohyctlPath": "C:\\evil.exe"` to a folder's `.vscode/settings.json`: it is ignored.
